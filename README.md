### 介绍

Chrome-KVM 基于 Chrome 浏览器开发的 BIOS 级远程控制项目。仅打开网页即可实现远程管理服务器或工作站，无需在被控机安装软件调整设置，实现无侵入式控制，适用范围广泛。

### 工具栏

控制页左侧边缘有一条可折叠的工具栏，收起后只在屏幕边缘留一截把手，点它展开。按钮从上到下分成四组：

| 图标     | 作用                                     |
|:-------|:---------------------------------------|
| 摄像机    | 视频状态，鼠标悬停看分辨率和帧率，点击可刷新或重开采集             |
| 键盘加鼠标  | 键鼠状态，鼠标悬停看固件和 USB 枚举情况，点击可刷新或重连         |
| 四角展开   | 全屏，进入后图标变为收拢状，并捕获 Win、Alt+Tab 等系统键        |
| 实心圆    | 录制当前画面，录制中变成红色方块，停止后自动下载 webm 文件        |
| 键盘     | 向被控端发送 Ctrl+Alt+Delete                 |
| 剪贴板    | 把本机剪贴板里的文本逐字符敲到被控端                      |
| 划掉的键盘  | 强制松开所有按键，用于被控端有键卡住时救场                   |
| 齿轮     | 打开设置页                                  |
| 双向箭头   | 刷新页面                                   |
| 尖括号    | 收起或展开工具栏                               |

两个状态图标共用一套配色：灰色未连接，绿色一切正常，黄色能用但有问题，红色已断开。

视频状态里，黄色表示采集卡没有画面输入或还没收到第一帧，红色表示采集中断（通常是采集卡被拔掉）或打开失败，悬停能看到具体原因，点一下会重新打开。

键鼠状态里，黄色的原因可能是 USB 未被被控端枚举、被控端已休眠、或芯片持续无应答已降级成只发不等；红色表示串口已断开。拔掉 CH9329 后插回会自动重连，也可以点图标立即重试。

粘贴功能通过模拟按键实现，因此只支持 US 键盘能直接打出的字符，中文等字符会被跳过并在结束时提示跳过了多少个。粘贴前会读取被控端的 Caps Lock 指示灯，亮着的话先帮你关掉，避免粘出来全是大写。

### 系统快捷键

Win、Alt+Tab、Esc、Ctrl+W 这些键平时会被本机的浏览器和系统先截走，根本到不了被控端。点工具栏的全屏按钮进入全屏后，页面会用 Chrome 的 Keyboard Lock 把它们全部拦下来转发过去——这时按 Win 弹的是被控端的开始菜单，Alt+Tab 切的也是被控端的窗口。

退出全屏要**长按 Esc 两秒**。这是 Chrome 强制保留的逃生口，短按的 Esc 会照常发给被控端，进 BIOS 正需要它。

只有点按钮进的全屏才有这个效果，按 F11 进的全屏不走 Fullscreen API，键盘锁定不生效。悬停全屏按钮可以看到当前是「已捕获」还是「未捕获」。

### 相对模式下的大幅移动

协议规定相对移动单包只能带 ±127，而实测一次快速甩动能请求到一千多个单位，直接截断会丢掉八成以上的距离——表现就是「甩一下，被控端光标只挪一点点」。

所以超过 127 的位移会**当场拆成多个包连发**（上限 `Ch9329.MAX_MOVE_BURST`，默认 16 包即 2032 单位），而不是截断丢弃，也不是攒到下一帧慢慢补——攒着发会让光标在手停下之后还滑行一段。超过上限的余量才留到下一帧，总位移不会丢。

这么做的前提是链路有富余。实测 1Mbps 下单包往返约 0.34ms，而 `mousemove` 事件间隔约 29ms，一个事件周期塞得下八十多个包，连发十几个包只占几毫秒。如果你把波特率调得很低（比如回到 9600，单包往返 20ms 以上），连发会明显跟不上，那时反而该把 `MAX_MOVE_BURST` 调小。

想知道自己这套链路的实际情况，在控制页的控制台里跑：

```js
ch.resetMoveStats()   // 清零，然后正常操作一会儿
ch.reportMoveStats()  // 看结果
```

`被合并丢弃` 不为 0 说明串口跟不上手速，该提波特率；`拆包连发次数` 和 `单轴最大请求位移` 反映你甩鼠标有多猛；`余量推迟次数` 不为 0 说明撞到了连发上限。

## 相对模式手感偏慢

指针锁定时拿到的是**未经本机加速的原始鼠标计数**（`unadjustedMovement: true`），原样下发给被控端。这是 KVM 该有的做法——本机再加速一次会和被控端自己的加速叠加，手感完全不可控——但副作用是比平时用桌面慢一截：平时操作系统的加速会在你快速移动时额外放大位移，这里有意关掉了。

两种补法，先试不用改代码的那个：

1. **调高被控端的指针速度**。缺点是改的是那台机器的全局设置，换一台被控端就得重调。
2. **调 `Ch9329.RELATIVE_SPEED`**（默认 1），跟着 KVM 走，对所有被控端生效。在控制页的控制台里直接改就能即时试手感：

```js
Ch9329.RELATIVE_SPEED = 1.8
```

它只影响相对模式；绝对模式发的是坐标，没有「倍数」这回事。

倍数会产生小数，零头会跨帧累积后补发，所以 `×1.5` 下连续十次位移 1 会精确送出 15 个单位，而不是被逐帧取整吃成 10。放大后超出 ±127 的部分由上面的拆包机制送出，不会又被截断——**这也是为什么倍数必须建立在拆包之上**：在那之前放大只会让更多位移撞上截断，放得越大丢得越狠。

## 鼠标模式与指针锁定

默认是**绝对模式**：本机光标在画面里的位置直接映射成被控端的坐标，两个光标一一对应，最直观。少数 BIOS 和老系统不认绝对坐标的 USB 鼠标，这时要在设置页改成**相对模式**，只上报位移。

**Android 必须用相对模式**：它只对相对鼠标显示指针，绝对鼠标会被当成触摸类设备，屏幕上看不到任何指针，像是鼠标没被识别。macOS 两种模式都能用（前提是芯片工作在模式 2，见下一节）。所以**模式 2 + 相对模式**是同时适配 macOS 和 Android 的组合，不用切换目标时反复改配置。

相对模式有个固有的坑：位移是靠本机光标的位置变化算出来的，光标一旦顶到屏幕边缘就不再动了，被控端光标也跟着卡在那边推不过去。所以进入相对模式后，**在画面上点一下会自动锁定指针**——本机光标随即隐藏并摆脱屏幕边界，想推多远推多远。按 **Esc** 释放。

锁定时会一并关掉本机的指针加速（`unadjustedMovement`），因为被控端自己还会再加一层，两层叠加会让鼠标很难控。平台不支持时会自动退回普通锁定。悬停键鼠状态图标可以看到当前是「指针已锁定」还是「点击画面锁定指针」。

绝对模式不需要也不会锁定指针，它要的就是真实光标坐标。

### 芯片工作模式（macOS 必读）

CH9329 出厂工作在**模式 0**：键盘 + 鼠标 + 自定义 HID 的三功能复合设备。Windows 下一切正常，但 **macOS 处理不好这种复合设备**，症状很有迷惑性：

- 相对模式下点击完全没反应，像是没连上；
- 绝对模式下能移动、能点击，**唯独拖不动**，再慢也拖不动。

原因是 macOS 没有绑定复合设备里的相对鼠标集合，只认了绝对鼠标，而它对绝对定位设备的拖拽支持很差。WCH 的数据手册对此有明确建议：Linux / Android / macOS 下使用**模式 2**（键盘 + 鼠标，去掉自定义 HID）。

在设置页选「2：键盘 + 鼠标」再点「写入工作模式」即可，**同样要把 CH9329 断电重插才生效**。改完后被控端会把它当成一台新键盘，macOS 可能弹出键盘识别向导——走完（按提示依次按 `Z` 和 `/` 即为美式布局）或直接关掉都行。

模式 2 同时包含键盘和鼠标——2019 年那版协议文档写的「模式 2 只有鼠标」已经过时，实测键鼠都在。

Windows、macOS、Android 三个被控端都实测过模式 2，均正常。模式 0 只在 Windows 下没问题，所以**没有理由留在模式 0**。

万一配置写乱了，设置页的「恢复出厂配置」会把参数和字符串描述符全部还原（波特率回到 9600、工作模式回到 0）。如果连串口都说不上话了，芯片还有硬件退路：**把 SET 引脚拉低，任何模式下都会强制切回协议传输模式**。

### 波特率

CH9329 出厂默认 9600bps，在 1080p 下快速移动鼠标时可能略显迟滞。设置页可以改：选好波特率后点「写入波特率」，**写入后需要把 CH9329 断电重插才生效**（协议规定参数下一次上电启用）。

控制页连接时会自动探测芯片实际使用的波特率，所以即使设置和芯片不一致也能连上，只是那一次连接每猜错一个候选会多花约一秒（上次连上的那个会优先尝试，正常情况下一次命中）。

可选的档位是 `Ch9329.BAUD_RATES`，下拉框由它生成，`setBaudRate()` 也只接受这里面的值。这不是多余的限制：**写进一个探测不到的波特率，芯片就再也连不上了**——「恢复出厂配置」本身也要求能和芯片通信，等于没有软件退路，只能去拉 SET 引脚。

要往上加档位，先确认两端都跟得上：

- **CH9329（无 F 后缀）只支持到 115200**，写更高的值会失联；CH9329F 标称到 15Mbps。
- USB 转串口那颗芯片同样是瓶颈：CH340 到 2Mbps，CH343 到 6Mbps。CH343 是全速 USB，手册建议**避开 3Mbps 及以上的连续通讯**，所以默认列表的上限压在 2M。

实际上 KVM 的数据包只有十几个字节，115200 下一包约 1ms，再往上收益很小——瓶颈会转移到 USB 往返延迟和应答等待上。

### 提示「打不开串口」

串口是独占的，同一个 CH9329 同时只能被一个页面打开。最常见的原因就是**另一个标签页还开着**——比如刚才用来写波特率的设置页，或者上次忘记关的控制页。关掉多余的标签页、只留一个控制页再刷新即可。

都关干净了还是打不开，就把 CH9329 拔下来重插。提示末尾的「详细信息」会列出每个波特率的尝试结果，`打不开串口` 是端口本身用不了，`打开成功但芯片无应答` 才是接线或芯片的问题。

### 开发

项目是纯静态页面，没有构建步骤，用任意静态服务器打开即可（Web Serial 要求 HTTPS 或 localhost）。

键鼠协议部分有一套不依赖任何外部库的测试，期望字节直接取自 CH9329 串口通信协议 V1.3 的命令样例：

```bash
npm test
```
